# Здание — это программа

**Типизированный, компилируемый IR для Autodesk Revit**

---

## 1. Слой, которого не хватало

Языковые модели хорошо пишут код. Здания они пишут плохо, и причина здесь структурная, а не
вопрос масштаба обучения.

Здание не помещается в контекстное окно: одна из моделей, на которых мы сверяемся, держит
**90 758 элементов**. Работа стейтфул — стена должна существовать раньше, чем в ней можно
разместить дверь, — и это состояние живёт в приложении, а не в файле, который можно сравнить
diff'ом. Она реентерабельна: одна и та же инструкция, поданная дважды, не должна породить две
двери. И она версионирована на шесть ладов: один и тот же замысел компилируется по-разному для
Revit 2021 и Revit 2026.

Поэтому сегодняшняя практика — заставить модель писать Revit C# напрямую, и арифметика этой
практики у нас перед глазами. Сложив логи с четырёх старых серверов, мы насчитали **85 374
вхождения кодов ошибок CS** — именно вхождения, не уникальные ошибки, и без дедупликации по
прогонам конвейера. Два кода дают **48.4%** от них — `CS1061` (32.3%) и `CS0117` (16.1%) — и оба это
один и тот же отказ: *обращение к члену Revit API, которого не существует*. Ещё ~10%
(`CS0104`/`CS0012`) — проблемы с namespace и ссылками на сборки. Грубо говоря, **около 60% этой
массы ошибок тратится на борьбу с поверхностью API**, а не на описание здания. (Источник:
`PROD_OP_DISTRIBUTION.md`, с оговорками самого отчёта о полноте логов и двойном счёте.)

**KIR — попытка его построить**: модель концентрируется на 3D,
геометрии и композиции, а единицы измерения, транзакции, версии API, хосты, свидетели и откаты
отдаются компилятору.

## 2. Всё целиком, одной картинкой

```
        ┌─────────────┐   typed ops (JSON)   ┌──────────────────────┐
        │   Python    │ ───────────────────► │       KIR            │
        │   brains    │                      │  parse → ground →    │
        │ (numpy,     │ ◄─────────────────── │  typecheck → plan →  │
        │  shapely,   │  typed refusal with  │  emit(per version) → │
        │  the model) │  candidates & route  │  gate → execute      │
        └─────────────┘                      └───────────┬──────────┘
                                                         │ C#, one TransactionGroup
                                                         ▼
   ┌────────────────┐   L0 → L1 → fold → materialize   ┌──────────────┐
   │  typed program │ ◄─────────────────────────────── │  live Revit  │
   │  + typed atoms │        (the reverse spine)       │  2021–2026   │
   └────────────────┘                                  └──────┬───────┘
                                                              │ read-back
                                            witness {geometry_ok,      │
                                                     semantic_ok,      │
                                                     topology_ok} ◄────┘
```

Важнее самих блоков — два свойства.

**Каждый вызов заканчивается ровно одним из двух типизированных исходов.** Либо
`{ok, per_op_results, witness}` — результат с доказательством, полученным обратным чтением, —
либо `{refused, diagnostics}` — машиночитаемый отказ с кандидатами и маршрутом к запасному пути.
Единственное запрещённое состояние — молча неверный ответ; `ok:true`, оборачивающий вложенную
ошибку, — постоянный регрессионный кейс со своим собственным тестом.

**IR работает в обе стороны.** Вперёд — типизированная программа становится C# под конкретную
версию, Revit его выполняет и затем читает результат обратно. Назад — живая модель декомпилируется
в такую же типизированную программу, и всё, что лифтер не может выразить, становится
**типизированным атомом с кодом причины**, а не молча пропадает. Именно обратное направление
превращает «мы умеем строить» в «мы умеем редактировать то, что уже существует».

Вот настоящая программа, полученная из Python SDK и напечатанная дословно:

```json
{
  "ir_version": "1.0",
  "intent": "one bay: wall + door + window",
  "ops": [
    {"op": "create_wall", "id": "wall1",
     "p0_mm": [0, 0], "p1_mm": [6000, 0],
     "level": {"by": "name", "value": "Level 1"}, "height_mm": 3300},
    {"op": "create_door", "id": "door1",
     "host": {"by": "ref", "value": "wall1"},
     "offset_mm": 1200, "sill_mm": -100,
     "symbol": {"by": "name", "value": "0915 x 2134mm"},
     "mirrored": false, "hand_flipped": false, "facing_flipped": false}
  ]
}
```

Обратите внимание, что именно *невыразимо*. У двери нет `xyz`: она — это `host` + `offset_mm`
вдоль хоста + `sill_mm`. «Окно, парящее в воздухе» — не случай, который мы валидируем, это
предложение, которое язык не может сформулировать. Любая длина — в миллиметрах; футов в IR не
существует. Координаты, которые иначе пришлось бы считать модели, считает компилятор.

## 3. Пять нитей одного решения

### 3.1 Выразительность и сжатие

Единица, которую пишет модель, — не элемент. Оболочка программы держит **20 написанных опов** и
раскрывается максимум до **320** (`compiler.MAX_OPS_PER_PROGRAM` / `MAX_VALIDATED_OPS`; собственный
потолок макро-слоя — 300). Измерено сегодня на Python SDK: один написанный оп `stack`, несущий
двенадцать колонн на типовом этаже, наращённый на 20 уровней с закруткой, раскрывается в **260
опов / 240 элементов** — один оп написала модель, 260 выполнит компилятор. У нескольких опов есть
собственный операнд-множество (`member_ops`, `placements`, `graph_nodes`/`graph_segments`,
`refs_w`), так что это свойство языка, а не одного макроса.

```python
import numpy as np
from kukai.ir import sdk

p = sdk.program(intent="tower with a waist")
with p.stack(levels=20, h_mm=3600,
             transform=sdk.transform(scale_xy_top=[0.8, 0.8],
                                     twist_deg_total=24)) as floor:
    for a in np.linspace(0, 2 * np.pi, 12, endpoint=False):
        floor.add(sdk.create_column(xy=[20000 * np.cos(a), 20000 * np.sin(a)],
                                    level=sdk.BY_MACRO, symbol="К 300x300"))

p.stats()   # {'ops_written': 1, 'ops_expanded': 260, 'elements': 240}
out = p.compile(version="2023", snapshot=snap)
```

Честность здесь держится на двух дизайн-правилах. В SDK **нет ни одного билдера, написанного
вручную** — по одной Python-функции на оп генерируется из реестра в момент импорта, так что
сигнатура не может разойтись со спекой. И SDK не добавляет **никакой семантики**: он не может
выразить ничего, чего нет в реестре, и не может спрятать отказ. У корректности ровно один
владелец.

### 3.2 Шесть версий, одна программа

`emit` по конструкции работает под конкретную версию: эмиттер ветвится (`Floor.Create` против
`doc.Create.NewFloor`), а оп, который версия не поддерживает, — это типизированный отказ
`KIR-E-VERSION`, а не сюрприз во время выполнения. Сгенерировать один раз и грепать тот же текст
против шести целей — значит изобретать несуществующие отказы; мы так делали и перестали.

Принуждение здесь — гейт: **каждая пишущая программа корпуса компилируется против реальных
reference-сборок Revit с 2021 по 2026**, а с 2026-07-28 — ещё и в обоих режимах изоляции (`atomic`
на всю программу и `per_op`). Текущее состояние, как его сообщает раннер гейта: **1 056 живых
компиляций Roslyn, PASS**. Добавление оси `per_op` сразу же вскрыло два дефекта, прожившие
незамеченными неделями — `CS0136` в `load_family` и ветку `in_view`, которая никогда не могла
скомпилироваться, — оба невидимые на оси `atomic`.

Гейт также научил нас быть осторожными с тем, что именно он доказывает. **Компиляция на шести
версиях и постройка в Revit — два разных утверждения**, и их нельзя цитировать как одно; мы держим
их в отдельных корпусах и выводим живое число заново из телеметрии, а не по памяти.

### 3.3 Субстрат, а не фича

Когда IR существует, возможности, каждая из которых иначе была бы отдельным проектом,
превращаются в конечные точки поверх одного субстрата. Сегодня подключены живьём четыре:
**`/run`** (выполнить типизированную программу со свидетелями), **`/decompile`** (прочитать живую
модель в типизированные опы плюс типизированные атомы), **`/rebuild`** (собрать декомпилированную
программу заново, чанками, под законами атомарности по хосту) и **`/idempotence`** (запустить одну
и ту же программу дважды и доказать, что второй запуск не добавляет ничего — id опов штампуются в
модель в той же транзакции, так что повтор идемпотентен, а «возобновить с опа K» — это просто
«пропустить проштампованное»). Пятая, **стенд-миссия** (§3.4), — офлайн-применение того же
компилятора в роли судьи. Ни одной из них не потребовался новый движок.

## Open-core, и чего мы хотим от вас

**Фреймворк становится опенсорсным 9 августа 2026.** Это формулировка плана — обязательство по
дате, а не уже достигнутый результат. В поставку идёт ядро компилятора: реестр, генераторы схемы и
грамматики, поэтапный конвейер, эмиттеры по версиям, механика свидетеля, хребет декомпиляции и
спеки, которые всем этим управляют (`SPEC_V1.md`, `KIR_DECOMPILE_SPEC.md`) — которые, начиная с
2026-07-28, наконец-то живут внутри репозитория, а не рядом с ним.

Три вещи, которые мы правда хотели бы получить от любого, кто прочтёт код:

1. **Сломайте свидетеля.** Найдите оп, чьё постусловие проходит, хотя Revit сделал что-то другое.
   Это самый ценный баг в этой системе, и именно поэтому теперь каждая проверка обязана называть
   ось, которую она читает.
2. **Прогоните обратное направление на здании, которого мы никогда не видели.** Покрытие на наших
   собственных моделях — это число про нас. Покрытие на ваших — число про компилятор, и каждый
   отказ записывается в очередь, которая решает, что язык выучит следующим.
3. **Поспорьте с границей.** Любая числовая граница в реестре, придуманная рассуждением вместо
   измерения, — это будущий молчаливый атом. Если для ваших проектов она неверна, мы предпочли бы
   узнать это от вашей модели, а не от нашей.

Мы продолжим публиковать числа, которые падают. Здание — это программа, а программа, которую
нельзя верифицировать, — это просто очень дорогое предложение на словах.
