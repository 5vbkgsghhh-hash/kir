# MERKLE_SPEC — контент-адресный Merkle-DAG слой декомпайла

Волна: `wave/merkle-dag` · база `prod-live` · модуль `kukai/ir/decompile/merkle.py`
Статус: дизайн + реализация + property-тесты (см. NOTES_FOR_LEAD.md для дельты suite).

---

## 0. Что уже было и что этот слой добавляет

`fold.py` уже несёт контент-адрес поддерева:

| Есть в fold.py | Роль |
|---|---|
| `canon_hash(node, origin_mm)` | рекурсивный канонический SHA-1 L1-листа / L3-поддерева |
| `_canonical_tree` | канонизация с **сортировкой детей** → порядок-независимость |
| `_canonical_l1` / `canon_op` / `_canonical_value` | канонизация листа: округление до `CANON_MM`, стрип `_VOLATILE_FIELDS`, `<level>`/`<ref>` заглушки |
| `_localize_coordinates` | вычитание origin → **инвариантность к переносу** |
| `stable_tree_id` | identity узла = kind + sorted source ids (НЕ контент) |

Чего не было: **стора** (hash→узел, общие поддеревья один раз), **dedup-отчёта**,
**diff** с ранним обрывом, **инкрементальной пересборки**. Их даёт этот слой.

Слой **надстраивает, не переизобретает**: канонизация значений — только через
`fold._canonical_l1` / `fold.canon_op` / `fold._canonical_value` / `fold._round_mm`
(fold остаётся единственным авторитетом «что значит одинаковая форма» на уровне
значений). Merkle добавляет ровно одно: **структуру DAG** — узел ссылается на
детей по хешу, а не телом.

## 1. Ключевая развилка: почему НЕ просто `canon_hash`

`canon_hash(node, origin)` канонизирует **всё поддерево против одного origin
корня вызова**. Следствия:

1. Два одинаковых санузла на одном этаже в разных XY получают **разные**
   канонические формы (их координаты локализованы против origin ЭТАЖА, а не
   против самих себя) → внутриэтажный dedup невозможен.
2. Узел не может ссылаться на ребёнка по хешу: тело ребёнка в каноне зависит
   от origin вызова. Без ссылок по хешу нет DAG, нет O(изменение) diff, нет
   «хранить один раз».

**Решение (классическая инстансная схема content+placement):**

- Каждый узел хешируется против **собственного канонического origin**:
  `node_origin(n)` = покомпонентный минимум по всем **реально локализованным
  точкам** точных L1-листьев поддерева — x/y из всех координатных векторов,
  z **только из настоящих 3D-векторов** (ось без данных → 0.0; всё округлено
  до `CANON_MM`). Origin — детерминированная функция контента, ковариантная
  переносу ⇒ локализованный контент инвариантен к переносу **на каждом
  уровне**, не только на уровне этажа.
  *Почему не `facts.bbox_min_mm` (первая версия дизайна, отвергнута на
  property-тестах):* fold's `_points_from_params` НУЛЁМ заполняет z у
  2D-точек параметров (`p0_mm:[x,y]`, `xy:[x,y]` — уровнево-относительные),
  поэтому bbox любого этажа выше нуля утаскивается к z=0 и одинаковые этажи
  на разных отметках переставали совпадать. Обнаружено тестом P1
  «4 одинаковых этажа → один узел», починено собственным сборщиком точек
  (`_leaf_points`), который различает 2D и 3D.
- Ребро родитель→ребёнок несёт `(child_hash, offset_mm)`, где
  `offset = child_origin − parent_origin` (обе величины кратны `CANON_MM` ⇒
  вычитание точное во float). Сдвиг ребёнка внутри родителя меняет offset ⇒
  меняет хеш родителя. **Ничего не теряется** — Р-3 соблюдён: одинаковый хеш
  корней ⟺ одинаковые здания (с точностью до общего переноса).
- Хеш узла = SHA-256 канонического JSON
  `{"v": "merkle/1", "content": …, "edges": sorted[(hash, offset)]}`.

Итог: одинаковая форма где угодно (в этаже, между этажами, между зданиями) =
один хеш = один узел в сторе; родители различают «где стоит» через offset.

### Отличия класса эквивалентности от `canon_hash` (намеренные, задокументированы)

| Аспект | canon_hash | merkle_hash | Почему |
|---|---|---|---|
| Алгоритм | SHA-1 | SHA-256, домен `merkle/1` | новый домен ключей; версионируется как `COMPILE_CACHE_WRAPPER_VERSION` |
| Origin | один на всё поддерево, задаёт вызывающий | свой у каждого узла, из контента | иначе нет DAG и нет вложенного dedup |
| `macro.cell` / `macro.cells` | в хеше (абсолютные индексы сетки) | **исключены** | производны от абсолютной позиции членов = placement, не форма; иначе перенос здания на 8 м менял бы хеш зон |
| `macro.base_z_mm` | в хеше (абсолютный Z) | **исключён** | то же: placement стека, а не его форма; несёт ребро |
| Всё остальное | — | идентично fold-канону | реиспользуются те же функции |

`canon_hash` **не тронут** — байт-в-байт прежний, это опора `_vertical_fold`.

Граница точности — та же, что у самого fold: `_round_mm` использует банковское
округление, поэтому на координатах ровно `*.5 мм` перенос на нечётное число мм
может изменить канон (это уже так в `canon_hash`). Слой не сужает и не
расширяет эту границу; property-тесты работают на сетке, не попадающей на .5.

## 2. Структуры

```python
class MerkleError(ValueError)                  # база, fail-closed
class MerkleCollisionError(MerkleError)        # один хеш — разный контент
class MerkleNodeMissingError(MerkleError, KeyError)   # get() отсутствующего
class MerkleIntegrityError(MerkleError)        # битый узел / битый персист

@dataclass(frozen=True) MerkleEdge:
    child_hash: str
    offset_mm: tuple[float, float, float]      # кратно CANON_MM

@dataclass(frozen=True) MerkleNode:            # ЧИСТАЯ ФОРМА, ноль identity
    hash: str                                  # sha256, вычислен из полей ниже
    kind: str
    content_json: str                          # канонический JSON payload/members/macro
    edges: tuple[MerkleEdge, ...]              # sorted (child_hash, offset)
    leaf_count: int                            # производное, для отчётов

@dataclass(frozen=True) Occurrence:            # привязка формы к живому зданию
    path: tuple[int, ...]                      # индексный путь от корня дерева
    node_id: str                               # stable_tree_id живого узла
    hash: str
    origin_mm: tuple[float, float, float]      # АБСОЛЮТНЫЙ origin вхождения
    tree_node: TreeNode                        # ссылка на живой узел (payload/members точные)

class MerkleIndex:                             # одно здание, один fold-корень
    root_hash: str; root_origin: tuple; label: str
    occurrences: dict[str, tuple[Occurrence, ...]]   # hash → все вхождения
```

Разделение ответственности (важно): **стор — библиотека форм** (никаких
element id — `_canonical_l1` их стрипает), **индекс — привязка** форм к
конкретным `TreeNode` c точными L1-payload. Пересборке нужны payload'ы — она
берёт их из индекса, стор остаётся анонимной библиотекой, шарящейся между
зданиями.

## 3. API

```python
# хеширование / индексация
merkle_hash(node: TreeNode) -> str
node_origin(node: TreeNode) -> tuple[float, float, float]
build_index(tree: TreeNode, *, label="", store: MerkleStore | None = None) -> MerkleIndex
    # один детерминированный обход; store переданный — наполняется put'ами

# DAG-store (в памяти; опц. дамп на диск, БЕЗ навязывания прод-БД)
class MerkleStore:
    put(node: TreeNode) -> str          # рекурсивно, дети раньше родителя
    get(hash: str) -> MerkleNode        # нет → MerkleNodeMissingError
    has(hash: str) -> bool
    __len__ / __contains__
    reconstruct(hash: str) -> dict      # каноническое вложенное дерево (аудит)
    dump_jsonl(path) / load_jsonl(path) # детерминированные байты; загрузка
                                        # ПЕРЕсчитывает хеш каждого узла,
                                        # сверяет kind и leaf_count с
                                        # покрытым хешем контентом (это
                                        # метаданные ВНЕ хеша — иначе их можно
                                        # подменить при валидном хеше),
                                        # проверяет замкнутость рёбер и
                                        # неразрешимые циклы — иначе
                                        # MerkleIntegrityError (fail-closed)

# dedup / библиотека компонентов
dedup_report(indexes: Sequence[MerkleIndex], *, min_occurrences=2,
             min_leaves=2) -> tuple[DedupEntry, ...]
    # DedupEntry: hash, kind, leaf_count, occurrence_count,
    #             by_building (sorted tuple), sample_label, savings, dominated
    # savings = leaf_count * (occurrence_count - 1); сортировка (-savings, hash)
    # Доминирование: запись доминируема, если КАЖДОЕ её вхождение лежит
    # строго внутри вхождений ДРУГИХ отчётных повторов (санузел, живущий
    # только внутри уже посчитанной типовой квартиры). Доминируемые скрыты
    # по умолчанию — отчёт отдаёт МАКСИМАЛЬНЫЕ повторы;
    # include_dominated=True возвращает всё с флагом. Следствие: два
    # идентичных здания дедупятся ОДНОЙ записью kind=building (корень).

# diff
diff_trees(index_a, index_b) -> MerkleDiff
    # MerkleDiff.entries: tuple[DiffEntry, ...]
    # DiffEntry: status ∈ {added, removed, changed, moved},
    #            kind, path_a, path_b, node_id_a, node_id_b, hash_a, hash_b,
    #            origin_a, origin_b, leaf_source_ids_a/b (для added/removed/moved)
    # MerkleDiff.pruned: int — сколько поддеревьев отсечено по равному хешу
    # MerkleDiff.changed_source_ids: frozenset — свёртка листов затронутого

# инкрементальная пересборка (интерфейс; live Revit НЕ гоняется)
incremental_plan(diff, index_a, index_b) -> RebuildPlan
    # RebuildPlan:
    #   reuse:    tuple[PlanReuse, ...]    # hash равен И абс. origin равен:
    #                                      #   ничего не делать; compile-verdict
    #                                      #   и exec-результат переносимы
    #   relocate: tuple[PlanRelocate, ...] # hash равен, origin сместился:
    #                                      #   форма та же — compile-verdict
    #                                      #   переносим (см. §5), exec заново
    #                                      #   (или будущий move-op)
    #   emit:     tuple[PlanEmit, ...]     # added/changed: листы B на re-emit
    #   retire:   tuple[PlanRetire, ...]   # removed: листы A на удаление
    # каждый entry несёт merkle-hash — готовый ключ для любого нижележащего кэша

# флаг (инертность)
merkle_enabled() -> bool    # env KUKAI_IR_MERKLE ∈ {1,true,yes,on}, default OFF
```

## 4. Алгоритм diff (выигрыш Merkle)

Рекурсия от пары корней; на каждом шаге:

1. `hash_a == hash_b` и origin равны → **обрыв**, поддерево не посещается
   (`pruned += 1`). Равные хеши + равные origin ⇒ равные канонические формы
   на равных местах ⇒ внутри нечего искать.
2. `hash_a == hash_b`, origin разные → `moved`, тоже **обрыв** (контент
   идентичен, изменилось только место — его несёт сама запись).
3. Иначе пара `changed` + спаривание детей тремя детерминированными раундами:
   - **R1 по (hash, origin):** мультимножества; равный hash с равным origin →
     невидимы (unchanged), равный hash с разным origin → `moved`
     (остатки сортируются по origin для детерминизма);
   - **R2 по node_id:** `stable_tree_id` = kind+source ids — «тот же узел,
     отредактирован» → рекурсия;
   - **R3 по пересечению source ids:** жадно, сортировка
     `(-overlap, path_a, path_b)`, только одинаковый kind, overlap > 0 →
     рекурсия («та же комната + один стул»: node_id сменился, но 90% id общие);
   - остаток → `added` / `removed` целыми поддеревьями.

Звучность: спаривание влияет только на *гранулярность* отчёта (changed-пара
против removed+added), никогда на корректность — ни один отличающийся лист не
может быть «съеден», т.к. невидимыми становятся только точные (hash, origin)
совпадения. Свойства (§6, P5): `diff(A,A) = ∅`; каждый реально изменённый лист
покрыт какой-то записью; ни одна запись не покрывает только неизменённые листы.

## 5. Срастание с кэшами (закон Р-3)

- **compile_cache**: его нормализатор стирает числовые литералы ⇒ вердикт
  компиляции не зависит от координат. Merkle-класс эквивалентности *строже*
  скелетной нормализации на путях emit'а (равные merkle-хеши ⇒ одинаковые
  канонические op'ы с точностью до чисел/имён ⇒ одинаковый скелет C#), поэтому
  перенос вердикта на `reuse` И `relocate` записи корректен по построению
  compile_cache, слой ничего не обещает сверх этого. Интеграция — **ключом**:
  entry несёт merkle-hash, вызывающий строит из него ключ своего кэша; сам
  merkle-слой кэшей НЕ дублирует и вердиктов НЕ хранит.
- **lift_cache**: ортогонален (кэширует L0→L1 до fold); merkle потребляет уже
  сфолженное дерево — совместное включение безопасно: одно ускоряет вход
  fold, другое — выход.
- Оба закона наследуются: слой меняет **как** (не пересобирать совпавшее),
  никогда **что** (эквивалентность инкремента и полной пересборки — P7).

## 6. Property-тесты (test_merkle.py, seeded PRNG — hypothesis в venv нет,
конвенция репо `test_pbt.py`)

Генератор: синтетические здания по образцу `test_fold.py` (этажи × элементы ×
комнаты, случайные но seeded) → реальные `lift_document` → `fold_document` —
слой тестируется на настоящем выходе конвейера, не на макетах.

| # | Свойство | Что доказывает |
|---|---|---|
| P1 | тот же документ → тот же root-hash; перестановка детей → тот же hash | стабильность, порядок-независимость |
| P2 | сдвиг всех координат на целые мм → тот же root-hash и тот же состав стора | инвариантность к переносу на всех уровнях |
| P3 | смена id / label / имён уровней → тот же hash; смена геометрии/типа → другой | volatile-поля вне хеша; форма — в хеше |
| P4 | корпус случайных зданий в один стор: put никогда не кидает коллизию; разные формы → разные хеши; повторный put идемпотентен | dedup-корректность, fail-closed put |
| P5 | `diff(A,A)=∅`; после случайного edit-скрипта: изменённые source ids ⊆ покрытия diff, unchanged-поддеревья не содержат ни одного изменённого листа | diff-звучность (⊇ реальных изменений, ничего не съедено) |
| P6 | внутри hash-равных поддеревьев записей нет; pruned > 0 при локальном изменении большого здания | ранний обрыв работает |
| P7 | мультимножество `canon_op(leaf, (0,0,0))` из reuse(A) ∪ relocate(B) ∪ emit(B) == все листы B; reuse-листы A байт-в-байт равны своим двойникам в B | **инкремент ≡ полная пересборка**; заодно проверяет точность композиции origin'ов |
| P8 | dump→load → идентичный стор; повторный dump → те же байты; порча байта / ребро в никуда / подмена хеша → MerkleIntegrityError; get отсутствующего → MerkleNodeMissingError; рукотворная коллизия → MerkleCollisionError | детерминизм персиста, fail-closed |
| P9 | K переставленных копий квартиры → dedup-отчёт даёт occurrence_count=K; та же квартира в двух зданиях → счёт через оба; узлов в сторе меньше суммы узлов деревьев | библиотека компонентов, межзданиевый dedup |

Плюс юнит-краевые: пустое здание, узел без bbox (origin (0,0,0)),
atom-cluster/zoned-режим, `merkle_enabled()` default-off.

## 7. Дисциплина

- **Universal**: слой работает только на хешах формы; ни одного имени/регекспа
  (в т.ч. НЕ опирается на `_MOP_RE` — известный баг универсальности fold, не
  эта волна); ноль знаний про LOT31.
- **Fail-closed**: все ошибки типизированы (§2), никакого тихого merge.
- **Инертно**: модуль ничем из конвейера не импортируется; orchestrator/fold
  не тронуты; frozen L0 1.0 не тронут; включение — явная конструкция объектов
  вызывающим + флаг `KUKAI_IR_MERKLE` (default OFF) для будущей проводки.
- **Детерминизм**: ни времени, ни random, ни зависимостей от порядка dict;
  все обходы и сериализации сортированы; дамп воспроизводим байт-в-байт.
